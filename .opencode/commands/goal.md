Autonomous execution of this goal: $ARGUMENTS

Work like Claude Code's own loop: **act, verify, re-assess, repeat — until done**, under the AGENTS.md "One-shot execution" rules. Do not stop after a single pass; stop only when the loop's exit conditions are met.

0. **Classify the goal — most goals are NOT builds.** Decide one class and state it in the first line of the plan:
   - **build** — new capability that does not exist yet.
   - **build-well** — quality work on existing surface: audit→fix, conformance, de-duplication, hardening, spec-truth-up.
   - **land** — integration/merge/release work.
     Then state the **definition of done** for this goal — the observable evidence that ends the loop:
   - build: feature works in a real walk + tests green.
   - build-well: a **named standard** (design-system doc, spec section, contract test, invariant, or user decision) is met, AND a gate keeps it met. If no standard can be named from the goal text, that is the one clarifying question — ask it before the loop starts, and nothing else.
   - land: merged with quoted evidence, or explicitly blocked with the blocker named.
1. **Log it first** — add the kanban card (SOP step 1), then branch: `feat/<name>` for build, `fix/<name>` or `test/<name>` for build-well, `chore/<name>` for land (config/doc-only work may stay on main).
2. **Plan once, up front** — a 3–6 step sketch of the likely path. It is a sketch: each loop iteration may re-plan freely when reality disagrees. Ask at most one clarifying question before the first edit (spent in step 0 if needed). After the first edit, questions are soft check-ins only: report an update or request genuinely missing information — never for approval, never to ask whether to continue.
3. **The loop — each iteration:** (a) **re-read the actual state** (git status, failing tests, the file itself — never trust memory of it); (b) **pick the single highest-value next action** toward the definition of done; (c) **do it** with conservative defaults for every unspecified detail — safest reasonable option, recorded; (d) **verify** it worked (run what it touches); (e) if the plan sketch no longer matches reality, re-draw it. Then ask: is the definition of done met? If no, next iteration. **Every iteration must measurably shrink the gap** — fewer failing tests, fewer violations, a journey step that now works. An action that changes bytes but not the gap is busywork: discard it and pick another. If two iterations in a row fail to shrink the gap, that is not STUCK — that is DRIFT: stop, name why the current approach cannot converge (wrong layer? wrong tool? missing prerequisite?), and re-plan from a different angle or exit with an honest partial verdict. Never polish in place of progress.
4. **Green is the floor, not the bar** — passing tests prove the work is _correct_, never _good_. Before "done", review your own diff as a hostile senior reviewer would: does it meet the standard's intent, not just its letter? Would it survive `git show` in six months? Specifically reject: hacks that satisfy the gate without fixing the defect (renaming to dodge a check, deleting a test's teeth, special-casing the tested input), one-off fixes where a small shared helper was obviously right (the duplication rule), dead code, commented-out code, TODOs left for the reader, style that contradicts the surrounding file, and any "it works" where the surrounding pattern does it more idiomatically. If the diff would embarrass you in review, it is not done — fix it in the same loop.
5. **Failures are not exit conditions** — on failures, group by root cause, fix the code (not the test, unless the test itself is wrong), re-run until green. Only a product decision or deleting user data may exit — then state the fix you'd apply and wait.
6. **Full gate, every loop** — lint, typecheck, tests before calling done; for build-well also **mutation-check the new gate** (break the thing it guards, confirm it fails, restore) — an unverified gate is a false sense of safety. Run the relevant `scripts/benchmark_*` if this touches training/inference/quantization/architecture.
7. **Exit conditions — the loop ends only on:**
   - **DONE**: the definition of done is verified by evidence (step 0), the full gate is green, AND the diff survived the hostile-review pass of step 4 → land it (merge only when green; if unrecoverable, revert the branch and explain why);
   - **BLOCKED**: a product decision or user-data deletion is required → state the exact decision and the fix you'd apply, then wait;
   - **STUCK**: the same failure repeats with no state change across two iterations → stop, report the loop, the root-cause hypothesis, and what you'd try next. Never spin.
   - **PARTIAL**: DRIFT after a re-plan attempt, or the loop ran out of a real constraint (disk, environment, foreign-territory file) → land what is genuinely green and valuable, revert what is not, and report exactly what remains with the next action. An honest partial beats a mediocre "done".
8. **Manager-style report** — the reader is an engineering manager: lead with the verdict (goal achieved? evidence?), then the major and specifically-decided details — design choices, ASSUMPTIONS, test/bench numbers, open risks. For build-well, the verdict is measured against the named standard ("meets DESIGN_SYSTEM.md §type-scale; ratchet baseline shrunk"), never just "fixed". Mention any plan deviation from step 2 and why reality won. **If the verdict is PARTIAL, say so plainly — never dress a partial up as done.** Omit working noise: musings, raw shell commands, tool transcripts. Include a detail only if it's relevant to the decision or an interesting engineering read, and keep even those collapsed/appendix-style.
