# Model load serves the wrong artifact — rebase onto main

User report 2026-11-12: "the model doesn't load well" — confirmed as
**wrong/garbage model output**, not latency, not a hard failure.

## Reproduced (this checkout, `feat/stackable-notifications`)

```
load_model("Qwen/Qwen2.5-0.5B-Instruct")
  → success=True, verified=True, model_type=slonet-native
  → soul_path = models/slonet-native/qt_1794132830.soul   ← WRONG FILE
  → 4 layers, vocab=5871, embed=128
```

Real Qwen2.5-0.5B (`config.json`): `vocab_size=151936`, `hidden_size=896`,
`num_hidden_layers=24`, `model_type=qwen2`. The app logs
`Autoload ok: Qwen/...` and serves a char-level toy model → garbage output.

Probe: `/tmp/opencode/probe_model_load.py` (run via `./scripts/python`).

## Root cause

`domain/infrastructure/_internal/model_loader.py:267` `_try_load_soul()`:

1. ignores `model_id` entirely;
2. globs `models/slonet-native/*.soul`, sorts by newest mtime;
3. loads `soul_files[0]`;
4. **relabels it with the requested `model_id`**.

`_load_inner()` calls it FIRST (line 139, "Priority: native .soul first"),
so every `ModelLoader.load()` inherits the wrong-artifact class.

## Why it is on this checkout

Branch `feat/stackable-notifications` is **191 commits behind `main`**
(merge-base `11007f58e`, 2026-11-03 16:41). Main fixed this on 2026-11-04 in
**`a7769616c`** (card `20261104_053224`): identity-based resolution
(exact stem → `hash:<prefix>` → `dataset:<sig>` → family id only when every
candidate shares `base_model` + a non-empty dataset signature; otherwise a
loud refusal listing candidates), plus `read_soul_identity()` in
`domain/inference/_internal/slo_format.py` — bounded 64 KB header read,
~0.2 ms vs ~1.3 s per checkpoint. Branch has 11 unique commits, all pushed
to `origin/feat/stackable-notifications`.

## Blast radius on this branch

- `apps/api/server/infrastructure/startup.py` `_autoload_model()` (eager
  autoload fallback) → `loader.load()` → **AFFECTED**
- `domain/shell/_internal/local_api.py:1059` `load_model(...)` → **AFFECTED**
- default lazy-guard boot (`_try_lazy_guard_autoload` →
  `from_slnc(resolved_path)`) → unaffected (resolves the path directly)
- manual UI load (`setup_providers(slonet_hf_id=...)` → `from_slnc`) →
  unaffected

So it fires when `SLO_LAZY_GUARD_AUTOLOAD=0`, `SLO_ENABLE_PROCESS_GUARD=0`,
a `.slnc` is missing, the lazy path throws, or via the shell.
