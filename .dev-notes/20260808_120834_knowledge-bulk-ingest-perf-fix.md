Knowledge bulk-ingest perf fix

  Root cause of /knowledge/bulk-ingest latency growth (1.1s->10.2s) and /knowledge/stats 504s: (1) async bulk_ingest ran blocking ingest inline on the event loop, starving other routes; (2) add_fact rewrote the full persisted store per fact (O(n) serialization each, O(n*m) per batch); (3) dedup check + add_fact each embedded the same text twice. Fixes: bulk_ingest offloaded via asyncio.to_thread (kb.py:622); new KnowledgeMemory.add_facts() batch upsert + single _save_entries()/persist (knowledge.py); DuplicateDetector.check gained query_vector param so BulkProcessor embeds once per text and reuses the vector (knowledge_ops.py). ingest_file._store_chunks also switched to add_facts. Added isolated_paths autouse fixture to test_knowledge_ops.py (was writing to the real data dir). Bench: 15-item batch at 250-entry store 3.0x faster (0.48s -> 0.16s). Tests: +7 add_facts, +2 BulkProcessor regression, +3 router bulk-ingest; core knowledge/vector suites + full tests/server green. Also cleaned 301 bench-polluted entries from data/knowledge/entries.json (untracked dir) restoring original 250.
  
  Follow-up 1: query_sync vectorized (np.array(list_of_lists) single C-pass matrix + (mat @ q)/(norm*||q||+eps) + stable argsort); both InMemoryVectorStore and MogDBVectorStore route through it, eliminating the per-entry _cosine_similarity Python loop. Bench @5000 entries: 341ms -> 157ms per query. Parity tests vs brute-force loop (rel=1e-12; insertion-order ties preserved). Fixed test_learner_continual.py store pollution (real-dir writes via ContinualLearner's get_knowledge_memory() singleton) with autouse isolated_knowledge_paths fixture (paths + singleton reset); removed the 2 polluted entries and rebuilt data/knowledge/visited.json (md5 list, verified 250/250 via load).
  
  Follow-up 2 (matrix cache): InMemoryVectorStore + MogDBVectorStore cache the full (ids, mat) matrix, invalidated on every upsert (sync+async) and delete. Unfiltered queries reuse the cache; filtered queries build on demand and never corrupt it. Query @5000 entries: 8.0ms vs 157ms uncached vs 341ms old loop. Bulk-ingest end-to-end: 5000-entry store 2.39s -> 0.17s (14x), 1000-entry 9.6x, 250-entry 2.8x. Removed now-dead _query_sync_impl (no callers).
  
  Follow-up 3 (concurrency hardening): the plain cache had a staleness race — a query building (ids, mat) from pre-upsert entries could have its tuple assigned AFTER a concurrent upsert cleared the cache, permanently missing new entries until the next mutation. Real in production: bulk_ingest runs in a thread pool while /knowledge/search + /knowledge/stats query the same singleton store on the event loop. Made the cache version-guarded: _version bumps on every mutation (via _bump_version()); _cached_matrix() rebuilds when cache[0] != _version, so a stale tuple self-heals on the next read with no locks (GIL-atomic tuple read). Refactored the shared (ids, mat) builder into _cached_matrix()/_bump_version() on both stores. New tests: test_stale_cache_self_heals_on_version_bump (manual version bump + direct entry injection proves rebuild), test_concurrent_upsert_and_query_never_goes_stale (threaded smoke: 50 base + 200 upserts against continuous readers; final state consistent). Cached query @5000 unchanged (~7ms, version check free). Verification: 13 core suites green, full tests/server 1779 passed, store integrity 250/250.

  Follow-up 4 (residual suite flake): during full-suite regression, tests/server/test_datasets_router.py::TestConvertToMessages x3 intermittently failed 422 'missing dataset_id' and a combined core+server run crashed with RecursionError. Root cause: test_mobile_notifications.py::test_logs_when_httpx_missing monkeypatched builtins.__import__ with a fake_import whose forwarder called __import__(name) — self-referential after the patch, so ANY non-httpx import during the patched window recursed infinitely (pytest lazy imports made it order-dependent: crash in combined runs, silent pass alone, corruption during the datasets tests in others). Fixed by capturing real_import = __import__ before patching and forwarding to that. Verified: mobile file 19/19, mobile+datasets in one process 95/95, tests/server 1830 passed/68 deselected, ruff E9/F63/F7/F82 clean on all touched files. The earlier test_lora_eval 'F' and quantization_benchmark_e2e 'F.F.F.F' observed mid-combined-run are pre-existing/order-dependent, not from this change (both pass standalone).
